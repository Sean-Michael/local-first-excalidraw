# Backlog after 1.2.0

Findings from two test runs on 2026-10-21:

- **Strong model:** Claude drew a Homebrew `brew install wget` sequence diagram and class diagram (`ai-newstand/tests/test.excalidraw`). Both came out well. The items below are polish.
- **Weak model:** `lfm2:24b-a2b` on Ollama was asked for "a sequence diagram of the assistant chat flow, referencing the code and using the shape library". It made 11 `create_diagram` calls and every one failed. 3 of them repeated a call that had already failed, word for word. It never read a source file, and nothing was drawn. Its earlier C4 and architecture runs each made a single call that drew 3 generic boxes.
- **Mid-size model:** `qwen3.5:9b` got the same prompt. It explored properly (5 file reads) and drew a sensible diagram with code links. Then it got stuck trying to edit a group by its group id, and the reply was cut off.

Source: the saved chat histories in `~/.local-first-excalidraw/chats/<drawing>/<chat>.json`. These record every tool call's arguments and result, plus the endpoint and model. OTEL tracing was off because the app-started daemon had no `OTEL_*` variables.

The weak-model run says more about the tool layer than about the model. Our harness let the model loop, dropped its mistakes without saying so, and gave error messages it couldn't act on.

Status: every item below is addressed in the working tree (not yet released). The repair and retry guard apply to the in-app assistant. MCP clients get the better error messages, but the MCP SDK still drops unknown fields before a tool sees them.

## Weak-model robustness (tools and agent loop)

- [x] **Unknown keys are dropped without a word.** *Done: `args.ts` `checkArgs` reports every ignored field, with the field probably meant ("nodes[0–1].type (did you mean `shape`?)"), as a note on the result.* `z.object` strips any field the schema doesn't know (`agent.ts` `z.object(def.input).safeParse`). In the lfm2 run, `type: "ellipse"` on a node (the schema calls it `shape`), `type: "message"` and `direction` on edges, and `from`/`to`/`style` on nodes all vanished. The model got a diagram it hadn't asked for and no feedback. Fix: report the dropped keys in the result ("ignored: nodes[0].type, did you mean `shape`?"). Or map common aliases (`type` → `shape` on nodes, `type: "message"` → `relation` on edges) and say that you did.
- [x] **Edges put under `nodes` (and nodes under `edges`).** *Done: `normalizeGraphArgs` moves them to the right list, maps `type` to `shape` or `relation`, and says what it changed.* The model mixed the two arrays up repeatedly. Fix: when a `nodes` entry has `from` and `to`, move it to `edges` and say so. When an `edges` entry has no `to` but looks like a node (it has `label` and `type`/`shape`), give that diagnosis instead of a missing-field error.
- [x] **The unknown-node error doesn't help the model recover.** *Done: the error names the missing id, suggests the nearest node id, lists every node id and says how to fix it. Missing nodes aren't created automatically, so a typo can't add a stray box.* `layout.ts:178` reports `Edge chat -> server references an unknown node`. List the node ids that do exist and suggest a fix: "add a node with id `server`, or drop this edge". An option to create missing nodes from their ids might be worth having too.
- [x] **Repeated validation errors flood the result.** *Done: one line per problem, `edges[0–10].to: missing (id of the node the edge points to)`.* One mistake repeated on 11 edges produced 22 lines of `expected string, received undefined → at edges[n].to`. Group them: "edges[0–10]: missing `to` (the target node id)". Each schema field should also have a one-line example the error can quote.
- [x] **Nothing stops identical retries.** *Done: a repeat of a failed call isn't run; the model is told it failed and why. After two refused repeats the turn stops with a message to the user.* The agent loop (`agent.ts`, `MAX_STEPS = 40`) let the model send the same failing call 5 times. Detect a repeat of a failed call's name and arguments. On the second repeat, say in the error that the call already failed and why. On the third, stop the turn with a message to the user.
- [x] **No routing for sequence diagrams.** *Done: the system prompt sends sequence diagrams to `mermaid_to_drawing`, and `create_diagram` with message edges adds a note saying so. A dedicated sequence tool is still open.* The model forced a sequence diagram into the layered graph and never called `diagram_reference`. Fix: when `create_diagram` gets `message`-type edges, or the user asked for a sequence diagram, return a hint that names `mermaid_to_drawing` with `sequenceDiagram`. Consider a dedicated sequence tool with lifelines, messages and fragments as structured input, so models don't have to write Mermaid.
- [x] **The model skipped "reference the code".** *Done: the system prompt opens with an explicit order of work (code, shapes, reference, draw, check). The prompt is otherwise unchanged; measure with the `sequence-code-shapes` eval before shortening it.* It listed 10 files and read none. For models without `vision` or below some capability tier, consider a shorter system prompt with an explicit order (read the code, then check the reference and shapes, then draw, then check). The current prompt is long and written for strong models.
- [x] **Shape lookup comes too late.** *Done: covered by step 2 of the same order of work.* The model called `list_shapes` after drawing. When the user mentions the shape library, the prompt or the first `create_diagram` result should push for `list_shapes` before drawing.
- [x] **`list_shapes` doesn't recognise a library by its slug.** *Done.* Shape keys start with the library slug (`system-design-components/…`), so the model passed `library: "system-design-components"` and got "No library matches", twice. The filter (`tools.ts:314`) only checks the library id and a substring of the display name. Also compare against `slug(libraryName)`.
- [x] **`insert_shape "arrow"` returns a list of icons.** *Done: primitive names point to the right tool, and ambiguous matches are de-duplicated.* lfm2 wanted a connector and got "matches several shapes" plus wireframe arrow icons, with `go-back-arrow` listed twice. When the query is a primitive (`arrow`, `line`, `rectangle`), point the model to edges, `connect_elements` or `add_elements` instead, and remove duplicate names from the list.
- [x] **Group ids are rejected as element ids.** *Done: `delete_elements` and `arrange_elements` accept a group id; `update_elements` explains it's a group and lists the members. Other unknown ids get a "did you mean".* `read_drawing` shows `groups=rjeRiDDD7Tyu`, so qwen passed that id to `update_elements` and `delete_elements` and got `Element "rjeRiDDD7Tyu" not found`. Either accept a group id (it stands for all its members), or say "that's a group; its members are …".
- [x] **`include_json` floods small contexts.** *Done: on Ollama, each tool result is capped at about a tenth of the context window. Ollama sets no output cap, so a "length" stop means the window filled; the message now says that and how to fix it.* qwen called `read_drawing include_json: true` on a 32k-context model and got a full element dump. Soon after, the reply was cut off ("output limit reached"). Clip the JSON harder when `contextLength` is small, or leave `include_json` out of the tools those endpoints get. Also confirm whether the cut-off was a full context or a real output cap, and say which in the message.
- [x] **Make tracing easy to switch on from the app.** *Done: Settings → Diagnostics → Record assistant traces, and `npm run chats`.* The macOS app starts the daemon without your shell environment, so tracing needs a manual `lfx serve`. Add a Settings toggle that writes `LFX_TRACE_FILE` to the state dir. A script that summarises a chat file or trace into calls, errors, repeats and files read would make comparing models a one-liner. The chat JSON is already enough to do it.
- [x] **Add an eval for this prompt with a small local model.** *Done: scenario `sequence-code-shapes`, `--model ollama:NAME` for `--via assistant`, and Repeats and Files read columns in the summary. Not yet run against lfm2.* Add the lfm2 prompt as a scenario under `evals/` and run it through `--via assistant` with a small Ollama model, so these fixes can be measured. Track failed tool calls, repeated calls, and whether a source file was read.

## Chat UI

- [x] **Failed calls are labelled as successes.** *Done.* `Chat.tsx:51` maps `create_diagram` to "Drew a diagram" whatever the outcome. In the lfm2 transcript every failed call reads "! Drew a diagram · 7 nodes". Use a failure label ("Couldn't draw the diagram") and a one-line reason when `ok` is false, and leave out the node count, since nothing was drawn.

## Drawing quality (from the Homebrew diagrams)

- [x] **Message labels cross lifelines.** *Done: Mermaid output has its lifelines cut behind every label that crosses them (`gapLifelines`). Applies to diagrams converted from now on.* Sequence message labels sit right on top of the lifelines they cross ("fetch formula JSON", "formula + deps", "GET bottle"). Mask each lifeline behind its label, or offset the label so it falls between lifelines.
- [x] ~~**No consistent font across diagrams.**~~ *Not a bug: both paths default to the hand-drawn font. The class diagram was Nunito because of the user's "make it more professional" request.* On one canvas the sequence diagram (Mermaid path) uses the hand-drawn font and the class diagram (`create_diagram`) uses the clean sans. Pick one default for both paths, or let the caller choose with a `font` option.
- [x] **`«abstract»` class names aren't italic.** *Done: the class recipe documents the stereotype as the marker.* UML convention marks an abstract class by italicising its name. Excalidraw can't italicise part of a text, so at least document the stereotype as the substitute.
- [x] **Unlabelled dependency edges (prompt).** *Done: the class recipe and its common mistakes ask for `«use»`/`«create»`/`«call»` on every dependency.* Most dependency arrows in the class diagram had no stereotype; only the one to Keg had `«create»`. Have the class-diagram recipe in `diagram_reference` ask for `«use»`/`«create»` on dependencies.
- [x] **Messages placed outside their fragment (judge check).** *Done: in the sequence recipe's common mistakes and in the judge's correctness criteria.* The model put `GET bottle` outside the `alt [bottle available]` fragment, so the request also runs in the build-from-source branch. This is a model error rather than a tool bug, but the eval judge could check that messages sit in the right fragment.

## From the lfm2 eval after these fixes

Run on 2026-10-21 with `sequence-code-shapes`: 7 tool calls, 1 harmless error, 0 repeats, and a diagram drawn (83% of checks). The model still read no code, used generic names, and drew the same diagram twice.

- [x] **Drawing the code without reading it.** *Done: when the request refers to the code and the turn hasn't read any, the first `create_diagram` result tells the model its names are guesses, and to read the code and fix the nodes in place. Once per turn; mentioned files count as read.*
- [x] **The same diagram drawn twice.** *Done: when most of a new diagram's node labels are already in the drawing, `create_diagram` notes that it added a second copy and how to remove it. This is in the daemon, so MCP clients get it too.*
- [x] **`find_symbol` references included drawings.** A model's own guessed names came back as "references" from the `.excalidraw` it had just drawn. *Done: drawings and libraries are skipped.*
- [x] **A missing folder wasn't explained.** Every run began with `dir: "src"`, which the project doesn't have. *Done: the error lists the project's top-level folders.*
- [x] **`mermaid_to_drawing` added second copies without a word.** *Done: it shares the duplicate check, matching participant and box labels while ignoring case and spacing ("Order Service" = "OrderService").*
- [x] **Invented code links were kept.** *Done: during an assistant turn, a `code` link to a file that doesn't exist is left off the element, with a note saying how to find the real file. MCP clients keep the old behaviour (linked, with a note).*
- [x] **Loops of identical successful lookups.** lfm2 sent the same `list_files` call about 20 times; each succeeded, so the failed-call guard never fired. *Done: a read-only call already made twice with the same arguments is refused with its earlier result, until something is written. After two refusals the turn stops.*
- [ ] **A dedicated sequence tool.** lfm2 drew a box-and-arrow flow for a sequence request and never reached Mermaid. Structured input (participants, messages, fragments) may suit small models better than writing Mermaid.
