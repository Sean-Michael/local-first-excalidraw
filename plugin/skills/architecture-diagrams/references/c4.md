# C4 model diagrams
<!-- keywords: c4, c4 model, system context, context diagram, container diagram, component diagram, system landscape, dynamic diagram, c4 deployment, architecture diagram, system design, software architecture, high level design, services, microservices, boundaries -->

The C4 model (Simon Brown, [c4model.com](https://c4model.com)) describes software as a hierarchy of abstractions, so you can zoom in like on a map:

- **Person:** a human user, role or persona.
- **Software system:** the highest level of abstraction, something that delivers value. A team usually owns one.
- **Container:** a separately runnable or deployable unit that executes code or stores data, such as a web app, SPA, mobile app, serverless function, database schema or bucket. This is not a Docker container, although it often maps to one.
- **Component:** a grouping of related functionality behind an interface, inside one container (a module, package, or set of classes).
- **Code:** classes, functions, tables.

C4 is notation-independent. What matters is that each diagram explains itself.

## The diagrams

| Diagram | Scope | Shows | Audience | Draw it? |
|---|---|---|---|---|
| System context | One software system | That system as one box, the people who use it, and the systems it talks to | Everyone, technical or not | Always |
| Container | One software system | Its containers, plus the people and external systems connected to them | Developers, architects, ops | Always |
| Component | One container | Its components, plus the containers and systems they touch | Developers, architects | Only when it adds value; for long-lived docs, generate it from code |
| Code | One component | Classes, interfaces | Developers | Rarely; IDEs do it better |
| System landscape | An organisation or department | All of its systems and people, with no single system in the middle | Everyone | Larger organisations |
| Dynamic | One feature or scenario | Numbered interactions between elements at any one level | Everyone | Sparingly, for complex or recurring flows |
| Deployment | One environment (prod, staging, dev) | Container instances mapped onto deployment nodes (nested) and infrastructure nodes (DNS, load balancers, firewalls) | Developers, infra, ops | Yes, one per environment that matters |

A container diagram deliberately leaves out clustering, replicas, load balancers and failover. Those vary by environment and belong in deployment diagrams.

The arc42 template's views line up with C4: section 3 (context and scope) is the system context, section 5 (building block view) is the container and component levels, section 6 (runtime view) is dynamic or sequence diagrams, and section 7 (deployment view) is deployment diagrams ([arc42 docs](https://docs.arc42.org/home/)).

## Notation

From the C4 notation guidance ([c4model.com/diagrams/notation](https://c4model.com/diagrams/notation)):

- **Title:** the type and scope, such as "Container diagram for Internet Banking System".
- **Key or legend:** explains every shape, colour, border style, line style, arrowhead and icon. Also explain acronyms, here or in the labels.
- **Elements:** each states its **name**, its **type** (Person, Software System, Container, Component), its **technology** (containers and components), and a short **description** of its responsibility.
- **Relationships:** each line is one relationship in one direction, labelled with the intent (avoid the bare word "Uses"). The label reads in the arrow's direction. Between containers, add the technology or protocol, such as `[JSON/HTTPS]`, `[SQL/TCP]` or `[AMQP]`.
- **Colour and shape:** free, but consistent across diagrams. Make sure the diagram still works in black and white and for colour-blind readers.

Common visual conventions, which are not mandatory:

- People are stick figures or rounded shapes.
- The system in scope is a strong colour, and external systems are gray.
- Data stores are cylinders.
- The boundary is a dashed box labelled with the system name.

## Excalidraw recipe

Label format for every element, three lines:

```
Name
[Container: Technology]
One-line responsibility
```

For people, use `[Person]`. For external systems, use `[Software System]`. Keep each line short (under ~30 characters) so boxes don't get huge.

### System context

```json create_diagram
{
  "path": "docs/diagrams/c4-context-shop",
  "direction": "TB",
  "title": "System context: Online shop",
  "nodes": [
    { "id": "customer", "label": "Customer\n[Person]\nBuys products online", "shape": "ellipse", "color": "gray" },
    { "id": "shop", "label": "Online Shop\n[Software System]\nCatalogue, cart, checkout", "color": "blue" },
    { "id": "payments", "label": "Stripe\n[Software System, external]\nCard payments", "color": "gray" },
    { "id": "email", "label": "SendGrid\n[Software System, external]\nTransactional email", "color": "gray" }
  ],
  "edges": [
    { "from": "customer", "to": "shop", "label": "Browses and buys using" },
    { "from": "shop", "to": "payments", "label": "Takes payments using" },
    { "from": "shop", "to": "email", "label": "Sends order emails using" }
  ]
}
```

People are ellipses here because their label is three lines long. A library figure (`stick-figures/stick-man`) puts its label under the icon, where an outgoing arrow in a TB layout runs straight through it. Use the figure only with a one-line label, or in an LR layout. Leave out back edges (here, "SendGrid delivers emails to Customer") unless they matter: `create_diagram` draws them straight back across the diagram.

After drawing it, make the external systems dashed so the distinction isn't colour alone. Take the ids from the result.

```json update_elements
{
  "path": "docs/diagrams/c4-context-shop",
  "updates": [
    { "id": "payments", "strokeStyle": "dashed" },
    { "id": "email", "strokeStyle": "dashed" }
  ]
}
```

### Container

The system boundary is a group. People and external systems stay outside it, before and after it in the flow.

```json create_diagram
{
  "path": "docs/diagrams/c4-container-shop",
  "direction": "LR",
  "title": "Container diagram: Online shop",
  "nodes": [
    { "id": "customer", "label": "Customer\n[Person]", "shape": "ellipse", "color": "gray" },
    { "id": "spa", "label": "Storefront\n[Container: React SPA]\nBrowse and checkout UI", "color": "blue", "group": "shop" },
    { "id": "api", "label": "Shop API\n[Container: Node.js]\nOrders, cart, pricing", "color": "blue", "group": "shop" },
    { "id": "worker", "label": "Order worker\n[Container: Node.js]\nPayment capture", "color": "blue", "group": "shop" },
    { "id": "db", "label": "Orders DB\n[Container: PostgreSQL]\nOrders, customers", "color": "green", "group": "shop" },
    { "id": "stripe", "label": "Stripe\n[Software System]\nCard payments", "color": "gray" }
  ],
  "groups": [{ "id": "shop", "label": "Online Shop [Software System]" }],
  "edges": [
    { "from": "customer", "to": "spa", "label": "Uses [HTTPS]" },
    { "from": "spa", "to": "api", "label": "Calls [JSON/HTTPS]" },
    { "from": "api", "to": "worker", "label": "Enqueues jobs [Redis]", "style": "dashed" },
    { "from": "api", "to": "db", "label": "Reads and writes [SQL]" },
    { "from": "worker", "to": "stripe", "label": "Captures payments [HTTPS]" }
  ]
}
```

Here the Redis queue is a technology on the edge label rather than a box. That keeps every edge between neighbouring layers. Draw the queue as its own node when it matters to the question (see `messaging-and-events.md`).

How `create_diagram` lays this out, and why the example is shaped this way:

- **Groups.** A group's frame is the bounding box of its members. It reads correctly only when the members fill a run of consecutive layers that no other node shares. Here, the people and external systems sit before and after the group.
- **First layer.** Leave the first layer ungrouped. Otherwise the frame's name collides with the title.
- **Long edges.** An edge that skips a layer is drawn straight, through whatever sits in between. Here, a `worker → db` edge would cross the API. Avoid such edges, or move the node they cross with `update_elements` after rendering.

### Component

The same pattern one level down. The group is the container (`"Shop API [Container: Node.js]"`), the nodes are its modules (`"OrderService\n[Component: TS module]\nPlaces and cancels orders"`), and neighbouring containers sit outside the group. Take component names from the source tree, and link each node to its file (see `living-diagrams.md`).

### Dynamic (collaboration style)

Use `create_diagram` with edge labels numbered in order: `"1. POST /orders"`, `"2. INSERT order"`, `"3. Enqueue fulfilment"`. Use the sequence style (`mermaid_to_drawing`, see `uml-behaviour.md`) when there are more than ~6 steps, or when replies matter.

### Deployment

Frames can't nest, so:

1. Use `create_diagram` with one group per innermost deployment node, named with its path and technology: `"prod › eks › api pod [Kubernetes Pod]"`. Container instances are the nodes. Infrastructure nodes (load balancer, DNS, WAF) sit outside the groups, using library shapes such as `system-design-components/load-balancer`.
2. `read_drawing` to get the frames' bounds.
3. Add each outer node (cloud region, VPC, cluster) as a dashed rectangle around them, with a text label in its top-left corner:

```json add_elements
{
  "path": "docs/diagrams/deploy-prod",
  "elements": [
    { "type": "rectangle", "id": "vpc", "x": 40, "y": 80, "width": 1100, "height": 520, "strokeStyle": "dashed", "strokeColor": "#495057", "backgroundColor": "transparent" },
    { "type": "text", "x": 56, "y": 92, "text": "AWS eu-west-1 › VPC prod [Deployment Node]", "fontSize": 16 }
  ]
}
```

Draw one diagram per environment, with the environment in the title: `"Deployment: production"`.

## Common mistakes

- **Mixing levels:** classes or tables in a container diagram, or technologies in a context diagram. Draw a second diagram instead.
- **Showing deployment on a container diagram:** load balancers, replicas, Kubernetes namespaces.
- **Unlabelled arrows, or arrows labelled "uses":** arrows that point both ways, or bidirectional arrows that hide two different relationships.
- **No type or technology on elements:** a reader can't tell a service from a database from a library.
- **A shared library drawn as a container:** libraries are code inside containers, not separately deployed things.
- **Queues and topics:** model each one as a container (or several). Better still, label the arrows `"Publishes OrderPlaced to [Kafka topic orders]"` rather than drawing an unexplained hub that everything points at.
- **No title, no legend, unexplained acronyms.**
- **Too many boxes:** past ~15-20 elements, split by subsystem or zoom out.
- **Diagrams that drift from the code:** see `living-diagrams.md`.
